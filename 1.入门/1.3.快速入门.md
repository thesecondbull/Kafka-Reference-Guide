本教程假定您是从头开始的，并且没有接触过Kafka或ZooKeeper。由于Kafka控制台脚本在基于Unix和Windows平台上有所不同，因此在Windows平台上使用bin\windows\代替bin/，并将脚本扩展名更改为.bat。

### **步骤1****:****下载****源代码**

[下载](https://www.apache.org/dyn/closer.cgi?path=/kafka/2.3.0/kafka_2.12-2.3.0.tgz "Kafka下载") 2.4.0版本并解压缩。

> tar -xzf kafka_2.12-2.4.0.tgz

> cd kafka_2.12-2.4.0

### **步骤2****:****启动服务器**

Kafka使用[ZooKeeper，](https://zookeeper.apache.org/)因此如果您还没有，请先启动ZooKeeper服务器。您可以使用kafka随附的脚本来快速获取单独脏节点ZooKeeper实例。

bin/zookeeper-server-start.sh config/zookeeper.properties

[2013-04-22 15:01:37,495] INFO Reading configuration from: config/zookeeper.properties (org.apache.zookeeper.server.quorum.QuorumPeerConfig)

...

现在启动Kafka服务器：

bin/kafka-server-start.sh config/server.properties

[2013-04-22 15:01:47,028] INFO Verifying properties (kafka.utils.VerifiableProperties)

[2013-04-22 15:01:47,051] INFO Property socket.send.buffer.bytes is overridden to 1048576 (kafka.utils.VerifiableProperties)

### **步骤3****:****建立****topic**

让我们用1个分区和1个副本创建一个名为"test"的topic：

bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --replication-factor 1 --partitions 1 --topic test

现在，如果我们运行list topic命令，便可以看到该topic：

bin/kafka-topics.sh --bootstrap-server localhost:9092 --list test

除了手动创建topic外，还可以将broker配置为在发布到不存在的topic时自动创建。

### **步骤4****:****发送一些消息**

Kafka带有一个命令行客户端，它将从文件或标准输入中获取输入，并将其作为消息发送到Kafka集群。默认情况下，每行将作为单独的消息发送。

运行生产者，然后在控制台中键入一些消息以发送到服务器。

bin/kafka-topics.sh --bootstrap-server localhost:9092 --list test

### **步骤5****:****启动消费者**

Kafka还有一个命令行消费者，它将消息转储到标准输出。

> bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic test --from-beginning

This is a message

This is another message

如果上面的每个命令都在不同的终端上运行，那么您现在应该能够在生产者终端中键入消息，并看到它们出现在消费者终端中。

所有的命令行工具都有其他选项。在不带参数的情况下运行该命令将显示用法信息。

### **步骤6****:****建立多****broker集群**

到目前为止，我们只针对一个broker，但这并不有趣。对于Kafka来说，单个broker只是一个大小为1的集群，因此除了启动更多的broker实例之外，没有什么太大的变化。为了感受一下，让我们将集群扩展到三个节点（仍然全部在本地计算机上）。

首先，我们为每个broker创建一个配置文件（在Windows上，使用copy命令代替）:

> cp config/server.properties config/server-1.properties

> cp config/server.properties config/server-2.properties

现在编辑这些新文件并设置以下属性:

config/server-1.properties:

    broker.id=1

    listeners=[PLAINTEXT://:9093](plaintext://:9093)

    log.dirs=/tmp/kafka-logs-1

 

config/server-2.properties:

    broker.id=2

    listeners=[PLAINTEXT://:9094](plaintext://:9094)

    log.dirs=/tmp/kafka-logs-2

broker.id属性是集群中每个节点的唯一且永久的名称。我们只需要覆盖端口和日志目录，这是因为我们都在同一台计算机上运行它们，并且希望所有broker都不要试图在同一端口上注册或覆盖彼此的数据。

我们已经有Zookeeper并启动了单个节点，因此我们只需要启动两个新的broker节点：

> bin/kafka-server-start.sh config/server-1.properties &

...

> bin/kafka-server-start.sh config/server-2.properties &

...

现在，创建一个具有三个复制因子的topic：

> bin/kafka-topics.sh --create --bootstrap-server localhost:9092 --replication-factor 3 --partitions 1 --topic my-replicated-topic

好的，但是现在有了集群，我们如何知道哪个broker在做什么？要查看，请运行"describe topics"命令:

> bin/kafka-topics.sh --describe --bootstrap-server localhost:9092 --topic my-replicated-topic

Topic:my-replicated-topic   PartitionCount:1    ReplicationFactor:3 Configs:

    Topic: my-replicated-topic  Partition: 0    Leader: 1   Replicas: 1,2,0 Isr: 1,2,0

输出说明，第一行给出了所有分区的摘要，另外每一行都给出一个分区的信息。由于该topic只有一个分区，因此只有一行。

· "leader"，分区读取、写入的节点，每个节点都将被分区随机选择为领导者。

· "replicas"，分区复制日志的节点列表，处于活动状态的节点，无论是否是leader。

· "isr"，是"in-sync"副本的集合，是副本的列表，处于活动状态并追随leader。

请注意，在我的示例中，节点1是topic唯一分区的leader。

我们可以在第一个创建的topic上运行相同的命令，以查看其位置：

bin/kafka-topics.sh --describe --bootstrap-server localhost:9092 --topic test

Topic:test  PartitionCount:1    ReplicationFactor:1 Configs:

    Topic: test Partition: 0    Leader: 0   Replicas: 0 Isr: 0

因此，这里没有任何惊喜 - 起初创建的topic没有副本，并且位于服务器0上，这是我们创建时集群中的唯一服务器。

我们向新的topic发布一些消息:

现在让我们消费这些消息:

> bin/kafka-console-producer.sh --broker-list localhost:9092 --topic my-replicated-topic

...

my test message 1

my test message 2

^C

> bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --from-beginning --topic my-replicated-topic

...

my test message 1

my test message 2

^C

现在让我们测试一下容错能力。Broker 1扮演leader的角色，所以让我们杀死它：

> ps aux | grep server-1.properties

7564 ttys002    0:15.91 /System/Library/Frameworks/JavaVM.framework/Versions/1.8/Home/bin/java...

> kill -9 7564

在Windows上使用:

> wmic process where "caption = 'java.exe' and commandline like '%server-1.properties%'" get processid

ProcessId

6016

> taskkill /pid 6016 /f

领导权已切换到关注者之一，并且节点1不再位于同步副本列表中：

> bin/kafka-topics.sh --describe --bootstrap-server localhost:9092 --topic my-replicated-topic

Topic:my-replicated-topic   PartitionCount:1    ReplicationFactor:3 Configs:

    Topic: my-replicated-topic  Partition: 0    Leader: 2   Replicas: 1,2,0 Isr: 2,0

但是，即使最初进行写操作的leader已经下线，消息仍然可以消费:

> bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --from-beginning --topic my-replicated-topic

...

my test message 1

my test message 2

^C

### **步骤7****:****使用Kafka Connect** **import/export****数据**

从控制台写入数据并将其写回到控制台是便捷的起步，但是您可能要导入其他来源的数据到Kafka或将数据从Kafka导出到其他系统。对于大多数系统，可以使用Kafka Connect导入或导出数据，而无需编写自定义集成代码。

Kafka Connect是Kafka附带的工具，用于将数据导入和导出到Kafka。它是运行connector的可扩展工具，connector实现与外部系统进行交互的自定义逻辑。在此快速入门中，我们将看到如何使用简单的连接器运行Kafka Connect，连接器将数据从文件导入到Kafka topic，并将数据从Kafka topic导出到另一文件。

首先，我们将从创建一些种子数据开始进行测试:

> echo -e "foo\nbar" > test.txt

或在Windows上:

> echo foo > test.txt

> echo bar >> test.txt

接下来，我们将启动两个*独立*运行的连接器。我们提供了三个配置文件作为参数。第一个是Kafka Connect进程的配置，其中包含通用配置，例如要连接的Kafka broker和数据的序列化格式。另外的配置文件指定要创建的连接器，包括唯一的连接器名称，要实例化的连接器类，以及连接器所需的其他配置。

> bin/connect-standalone.sh config/connect-standalone.properties config/connect-file-source.properties config/connect-file-sink.properties

示例（随Kafka一起提供）使用之前启动的集群配置，并创建两个连接器：第一个是source连接器，它从输入文件中读取行并将每行生成到Kafka topic，第二个是接收器连接器，从Kafka topic读取消息，并在输出文件中作为一行显示。

在启动过程中，您将看到许多日志消息，其中包括一些正在实例化连接器的消息。Kafka Connect进程启动后，source连接器应开始从test.txt中读取行并将其生成到topic connect-test，而接收器连接器开始从topic connect-test中读取消息并将其写入文件test.sink.txt。我们可以通过检查输出文件的内容来验证数据已通过整个管道被传递：

> more test.sink.txt

foo

bar

请注意，数据存储在Kafka topic connect-test中，因此我们也可以运行控制台消费者以查看topic中的数据（或使用自定义消费者代码进行处理）：

> bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic connect-test --from-beginning

{"schema":{"type":"string","optional":false},"payload":"foo"}

{"schema":{"type":"string","optional":false},"payload":"bar"}

...

连接器继续处理数据，因此我们可以将数据添加到文件中，并查看它在管道中的移动情况:

> echo Another line>> test.txt

您应该看到该行出现在控制台消费者和接收器文件中。

### **步骤8****:****使用Kafka Streams处理数据**

Kafka Streams是用于构建关键实时应用程序和微服务的客户端库，其中输入或输出数据存储在Kafka集群中。Kafka Streams结合了在客户端部署Java和Scala应用程序的简便性以及Kafka服务器端集群技术的优势，使这些应用程序具有高度伸缩性、弹性、容错性、分布式等等。此[快速入门示例](http://kafka.apache.org/23/documentation/streams/quickstart)将演示如何运行流应用程序。
