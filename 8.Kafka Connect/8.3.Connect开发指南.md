本指南介绍了开发人员如何编写新的Kafka Connect连接器，以在Kafka和其他系统之间同步数据。它简要回顾了一些关键概念，然后描述了如何创建简单的连接器。

### 1.1.1. **核心概念和API**

#### 1.1.1.1. **连接器和任务**

要在Kafka和其他系统之间复制数据，用户需要为提取或推送数据的系统创建一个Connector。连接器有两种形式：SourceConnectors导入数据到kafka（例如，JDBCSourceConnector将关系数据库导入Kafka）和SinkConnectors导出kafka的数据（例如，HDFSSinkConnector将Kafka topic的内容导出到HDFS文件）。

Connectors不需要执行数据复制：它的配置描述了要复制的数据，并且Connector负责将作业分解为一组可以分发给worker的Tasks。这些Tasks也有两种相应的风格：SourceTask和SinkTask。

每个Task都在分配任务后负责将数据子集导入到Kafka或导出Kafka数据。在Kafka Connect中，始终将这些分配构造为一组输入或输出流，这些输入和输出流由相同模式的记录组成。这种映射是显而易见的：每个日志文件都可以被视为一个流，每行使用相同的模式解析形成一条记录，offset作为字节存储在文件中。在其他情况下，这样模型映射可能需要花费更多精力：JDBC连接器可以将每个表映射到流，但是offset需要自定义。一个可能的映射是使用timestamp列来用作offset。

#### 1.1.1.2. **流和记录**

每个流都应是键值对。键和值都可以使用复杂结构（提供了许多原始类型），但也可以使用数组、对象和嵌套的数据结构。运行时数据格式不采用任何特定的序列化格式；此转换由框架内部处理。

除了键和值之外，记录（由源生成的记录和传递至接收器的记录）都具有关联的流ID和offset。框架使用它们来定期提交已处理数据的offset，以便在发生故障时，可以从上次提交的offset开始恢复处理，从而避免了不必要的重复。

#### 1.1.1.3. **动态连接器**

并非所有作业都是静态的，因此Connector实现还负责监控外部系统是否可能需要重新配置。例如，在JDBCSourceConnector示例中，Connector可能会为每个表分配一组Task。创建新表时，它必须发现这一点，以便Tasks可以通过更新其配置将新表分配给其中一个。当发现需要重新配置（或Tasks数量的更改）时，它会通知框架，并且框架会更新任何对应的Tasks。

### 1.1.2. **开发一个简单的连接器**

开发连接器仅需要实现Connector和Task两个接口。Kafka源代码的file包中包含一个简单的示例。该连接器用于独立模式，并具有SourceConnector/SourceTask的实现，以读取文件的每一行并将其作为记录发出，以及SinkConnector/SinkTask的实现将每个记录写入文件。

本节的其余部分将逐步介绍一些代码，以演示创建连接器的关键步骤，但是开发人员还应参考完整的示例源代码，这里为简洁起见，省略了许多详细信息。

#### 1.1.2.1. **连接器示例**

我们将以一个简单的示例介绍SourceConnector，SinkConnector实现非常相似。首先创建继承自SourceConnector的类，并添加几个字段，这些字段将存储已解析的配置信息（要读取的文件名和要发送数据的topic）:

**public** **class** FileStreamSourceConnector **extends** SourceConnector {

    **private** String filename;

    **private** String topic;

实现了最简单的taskClass()方法，它定义了读取数据的类:

@Override

**public** Class<? **extends** Task> taskClass() {

    **return** FileStreamSourceTask.**class**;

}

下面定义FileStreamSourceTask类。添加一些标准的生命周期方法start()和stop():

@Override

**public** **void** start(Map<String, String> props) {

    // The complete version includes error handling as well.

    filename = props.get(FILE_CONFIG);

    topic = props.get(TOPIC_CONFIG);

}

 

@Override

**public** **void** stop() {

    // Nothing to do since no background monitoring is required.

}

最后，在taskConfigs()中实现真正核心。在这种情况下，我们只处理一个文件，因此即使可以根据maxTasks参数生成更多任务，我们也会返回只包含一个条目的列表:

@Override

**public** List<Map<String, String>> taskConfigs(**int** maxTasks) {

    ArrayList<Map<String, String>> configs = **new** ArrayList<>();

    // Only one input stream makes sense.

    Map<String, String> config = **new** HashMap<>();

    **if** (filename != **null**)

        config.put(FILE_CONFIG, filename);

    config.put(TOPIC_CONFIG, topic);

    configs.add(config);

    **return** configs;

}

尽管未在示例中使用，但SourceTask还提供了两个API在源系统中提交offset，它们是commit和commitRecord。这些API是为具有消息确认机制的源系统提供的。覆盖这些方法后，一旦源连接器被写入Kafka，就可以批量或单独地确认源系统中的消息。commit API存储offset到源系统中，直到通过轮询返回这个offset的确认为止。该API的实现应阻塞，直到提交完成。写入Kafka后，commitRecord API保存每个SourceRecord写入到源系统的offset。由于Kafka Connect自动记录offset，SourceTask不需要实现它们。如果连接器确实需要在源系统中确认消息，则通常仅需要一个API。

即使有多个任务，这种方法的实现通常也非常简单。它只需要确定输入任务的数量，这可能需要联系提取数据的远程服务方，然后再将它们分开。由于在任务之间分配工作的模式非常普遍，因此提供了一些实用程序ConnectorUtils来简化这些情况。

注意，此简单示例不包含动态输入。有关如何触发对任务配置的更新，请参见下一节的讨论。

#### 1.1.2.2. **任务示例-****source****任务**

接下来，我们将描述SourceTask的相应实现。该实现很短，但其实它的内容很多，无法完全涵盖在本指南中。我们将使用伪代码描述大多数情况的实现，具体您可以参考源代码中的完整示例。

与连接器一样，我们需要创建一个从基类Task继承的类。它还具有一些标准的生命周期方法:

**public** **class** FileStreamSourceTask **extends** SourceTask {

    String filename;

    InputStream stream;

    String topic;

 

    @Override

    **public** **void** start(Map<String, String> props) {

        filename = props.get(FileStreamSourceConnector.FILE_CONFIG);

        stream = openOrThrowError(filename);

        topic = props.get(FileStreamSourceConnector.TOPIC_CONFIG);

    }

 

    @Override

    **public** **synchronized** **void** stop() {

        stream.close();

    }

这是稍微简化的版本，相对简单，并且它们执行的唯一工作是分配或释放资源。这里有两点需要注意。首先，start()方法没有考虑从上一个offset恢复的情况，这将在后续部分中解决。其次，stop()方法是同步的，这是必要的，因为SourceTasks为它们提供了一个可以无限期阻塞的专用线程，因此需要通过Worker中其他线程的调用来停止它们。

接下来，我们实现任务的主要功能，即从输入系统获取事件并返回List<SourceRecord>的poll()方法:

@Override

**public** List<SourceRecord> poll() **throws** InterruptedException {

    **try** {

        ArrayList<SourceRecord> records = **new** ArrayList<>();

        **while** (streamValid(stream) && records.isEmpty()) {

            LineAndOffset line = readToNextLine(stream);

            **if** (line != **null**) {

                Map<String, Object> sourcePartition = Collections.singletonMap("filename", filename);

                Map<String, Object> sourceOffset = Collections.singletonMap("position", streamOffset);

                records.add(**new** SourceRecord(sourcePartition, sourceOffset, topic, Schema.STRING_SCHEMA, line));

            } **else** {

                Thread.sleep(1);

            }

        }

        **return** records;

    } **catch** (IOException e) {

        // Underlying stream was killed, probably as a result of calling stop. Allow to return

        // null, and driving thread will handle any shutdown if necessary.

    }

    **return** **null**;

}

同样，我们省略了一些细节，但是我们可以看到重要的步骤：poll()方法将被重复调用，并且对于每个调用，它将循环尝试从文件中读取记录。对于读取的每一行，它还跟踪文件offset。它使用此信息创建SourceRecord，其中包含以下四项输出信息：源分区（只有一个，正在读取单个文件）、源offset（文件中的字节offset）、输出topic名称和输出值（这一行，我们包含了一个模式，指示这个值将始终是一个字符串）。SourceRecord构造函数的其他变量也可以包括特定的输出分区、key和header。

请注意，此实现使用常规Java InputStream接口，如果没有可用数据，则可能会休眠。这是可以接受的，因为Kafka Connect为每个任务提供了专用线程。尽管任务实现必须符合基本poll()接口，但是它们在实现方式方面具有很大的灵活性。在这种情况下，基于NIO的实现会更加高效，但是这种简单的方法可以工作，实现起来很快并且与Java的较早版本兼容。

#### 1.1.2.3. **任务示例-****接收器****任务**

上一节介绍了如何实现简单的SourceTask。与SourceConnector和SinkConnector不同，SourceTask和SinkTask具有非常不同的接口，因为SourceTask使用轮询接口而SinkTask使用push接口。两者共享通用的生命周期方法，但是SinkTask接口却大不相同：

**public** **abstract** **class** SinkTask **implements** Task {

    **public** **void** initialize(SinkTaskContext context) {

        **this**.context = context;

    }

 

    **public** **abstract** **void** put(Collection<SinkRecord> records);

 

    **public** **void** flush(Map<TopicPartition, OffsetAndMetadata> currentOffsets) {

    }

SinkTask文档包含完整的细节信息，但是该接口几乎与SourceTask一样简单。put()方法包含大多数实现，接受SinkRecords的集合，执行所需的转换并将它们存储在目标系统中。此方法在返回之前无需确保已将数据完全写入目标系统。实际上，在许多情况下，内部缓冲非常有用，因此可以一次性发送一整批记录，从而减少了向下游数据存储插入事件的开销。SinkRecords包含与SourceRecords基本相同的信息:Kafka主题、分区、偏移量、事件键和值，以及可选的header。

flush()方法在offset提交过程中使用，该方法允许任务从故障中从安全点恢复，从而不会丢失任何事件。该方法应将所有未完成的数据推送到目标系统，然后阻塞直到确认写入。offsets参数通常可以忽略，但是在某些实现中需要将offset信息存储在目标存储区中以提供精确一次交付。例如，HDFS连接器可以执行此操作，并使用原子移动操作来确保flush()自动将数据提交到HDFS。

#### 1.1.2.4. **从先前的****offset****恢复**

SourceTask实现包括每个记录的流ID（输入文件名）和offset（文件中的位置）。框架使用它定期提交offset，以便在发生故障的情况下，任务可以恢复并最大程度地减少重新处理和可能重复的事件数量（如果Kafka Connect正常停止，则从最新的offset恢复，例如在独立模式下或由于作业重新配置）。该提交过程由框架完全自动化，但是只有连接器知道如何返回输入流中的正确位置才能从该位置恢复。

为了在启动时正确恢复，任务可以使用SourceContext传递给initialize()方法来访问offset数据。在initialize()中，我们将添加更多代码以读取offset（如果存在）并寻求该位置：

stream = **new** FileInputStream(filename);

Map<String, Object> offset = context.offsetStorageReader().offset(Collections.singletonMap(FILENAME_FIELD, filename));

**if** (offset != **null**) {

    Long lastRecordedOffset = (Long) offset.get("position");

    **if** (lastRecordedOffset != **null**)

        seekToOffset(stream, lastRecordedOffset);

}

当然，您可能需要为每个输入流读取许多键。OffsetStorageReader接口还允许您发出批量读取以有效加载所有offset，然后通过将每个输入流搜索到适当位置来应用它们。

### 1.1.3. **动态输入/输出流**

Kafka Connect旨在定义批量数据复制作业，例如复制整个数据库，而不是创建许多作业来分别复制每个表。这种设计的结果是，连接器的一组输入或输出流可以随时间变化。

源连接器监控源系统更改，例如数据库中表的添加/删除。当他们更改时，应通过ConnectorContext对象通知框架必须重新配置。例如，在SourceConnector中：

**if** (inputsChanged())

    **this**.context.requestTaskReconfiguration();

该框架将立即请求新的配置信息并更新任务，从而使他们能够在重新配置任务之前优雅地提交其进度。请注意，在SourceConnector中，此监视目前由连接器实现完成。如果需要额外的线程来执行此监视，则连接器必须自己分配它。

理想情况下，此用于监视更改的代码应与Connector隔离，并且任务无需担心它们。但是，更改也会影响任务，最常见的是在输入系统中销毁它们的输入流之一时（例如，从数据库中删除表时）。如果任务在连接器之前遇到问题(如果连接器需要轮询更改，这将是常见的问题)，则任务将需要处理后续错误。值得庆幸的是，这通常可以通过捕获并处理适当的异常来简单地处理。

SinkConnectors通常只需要处理添加的流，这些流可以转换为输出中的新条目(例如，一个新的数据库表)。框架管理对Kafka输入的任何更改，例如，由于正则表达式订阅而导致输入topic集更改时。SinkTasks应该期望新的输入流，这可能需要在下游系统中创建新的资源，比如数据库中的新表。在这些情况下，最棘手的情况可能是第一次看到新输入流的多个SinkTasks与同时尝试创建新资源之间的冲突。另一方面，SinkConnectors通常不需要特殊的代码来处理动态流。

### 1.1.4. **连接配置验证**

通过Kafka Connect，您可以在提交执行连接器之前验证连接器配置，并可以提供有关错误和建议值的反馈。为了利用这点，连接器开发人员需要提供config()的实现，以将配置定义暴露给框架。

以下FileStreamSourceConnector的代码中定义了配置并将其暴露给框架。

**private** **static** **final** ConfigDef CONFIG_DEF = **new** ConfigDef()

    .define(FILE_CONFIG, Type.STRING, Importance.HIGH,"Source filename.")

    .define(TOPIC_CONFIG, Type.STRING, Importance.HIGH,"The topic to publish data to");

 

**public** ConfigDef config() {

    **return** CONFIG_DEF;

}

ConfigDef类用于指定预期的配置集。对于每个配置，您可以指定名称、类型、默认值、文档、组信息、组中的顺序、配置值的宽度以及适合在UI中显示的名称。另外，您可以通过覆盖Validator类来提供用于单个配置验证的特殊验证逻辑。此外，由于配置之间可能存在依赖关系，例如，配置的有效值和可见性可能会根据其他配置的值而改变。为了处理这个问题，ConfigDef允许您指定配置的依赖项，并提供一个推荐的实现来获取有效值，并根据当前的配置值设置配置的可见性。

此外，连接器中的validate()方法提供了一个默认的验证实现，该实现返回允许的配置列表以及配置错误和每个配置的推荐值。但是，它没有使用配置验证的推荐值。您可以为自定义配置验证提供默认实现的覆盖，该实现可以使用推荐的值。

### 1.1.5. **使用****Schema**

FileStream连接器就是很好的例子，因为它们很简单，但是它们也有一些简单的结构化数据——每一行只是一个字符串。几乎所有实际的连接器都需要具有更复杂数据格式的模式。

要创建更复杂的数据，需要使用Kafka Connect数据API。除了基本类型之外，大多数结构化记录还需要与两个类交互:Schema和Struct。

API文档提供了完整的参考，但下面是一个创建模式和结构（Schema和Struct）的简单示例：

Schema schema = SchemaBuilder.struct().name(NAME)

    .field("name", Schema.STRING_SCHEMA)

    .field("age", Schema.INT_SCHEMA)

    .field("admin", **new** SchemaBuilder.**boolean**().defaultValue(**false**).build())

    .build();

 

Struct struct = **new** Struct(schema)

    .put("name","Barbara Liskov")

    .put("age", 75);

如果正在实现源连接器，则需要决定何时以及如何创建模式。在可能的情况下，您应该尽可能避免重新计算它们。例如，如果您的连接器保证有一个固定的模式，那么就静态地创建它并重用单个实例。

然而，许多连接器将具有动态模式。一个简单的例子是数据库连接器。即使只考虑单个表，也不会为整个连接器预定义模式(因为它随表而异)。但是，在连接器的生命周期内，也可能无法修复单个表的问题，因为用户可以执行ALTER table命令。连接器必须能够检测到这些更改并做出适当的反应。

接收器连接器通常比较简单，因为它们消费数据，因此不需要创建模式。但是，他们应该尽可能仔细地验证他们接收的模式是否具有预期的格式。当模式不匹配时(通常指示上游生产者正在生成无法正确转换到目标系统的无效数据)，接收连接器应该抛出异常，以向系统指示此错误。

### 1.1.6. **Kafka Connect管理**

Kafka Connect的[REST层](#connect_rest)提供了一组api来支持集群的管理。这包括用于查看连接器配置和其任务状态的api，以及用于更改其当前行为(例如更改配置和重新启动任务)的api。

当连接器首次提交给集群时，将在连接工作进程之间触发一个再平衡，以分配由新连接器的任务组成的负载。当连接器增加或减少它们需要的任务数量、更改连接器的配置、添加或从组中删除工作线程(作为Connect集群有意升级的一部分)或由于故障时，也会使用相同的重新平衡过程。

在2.3.0之前的版本中，连接worker将重新平衡集群中的所有连接器及其任务，以确保每个worker的工作量大致相同。仍然可以通过设置connect.protocol=eager来启用此行为。

从2.3.0开始，Kafka Connect在默认情况下使用一种协议，该协议执行[增量协作再平衡](https://cwiki.apache.org/confluence/display/KAFKA/KIP-415:+Incremental+Cooperative+Rebalancing+in+Kafka+Connect)，在连接worker之间增量地平衡连接器和任务，只影响新任务、要删除的任务或需要从一个worker移动到另一个worker的任务。在重新平衡期间，其他任务不会停止或重新启动，就像旧的协议一样。

如果连接worker有意或由于故障离开了组，连接将在触发重新平衡之前等待schedule .rebalance.max.delay.ms。这个延迟默认为5分钟(300000ms)，以容忍worker的失败或升级，而无需立即重新分配离开worker的负载。如果这个worker在配置的延迟内返回，它将完全获得先前分配的任务。然而，这意味着直到schedule .rebalance.max.delay.ms指定的时间结束之前，这些任务都是未分配的。如果一个worker没有在这个时间限制内返回，Connect将在Connect集群中的剩余worker之间重新分配这些任务。

当组成Connect集群的所有worker都配置了protocol=compatible时，将启用新的Connect协议。当缺少此属性时这也是默认值。因此，当所有worker升级到2.3.0时，升级到新的Connect协议将自动发生。当最后一个worker加入2.3.0版本时，Connect集群的滚动升级将激活增量协作再平衡。

您可以使用REST API查看连接器的当前状态及其任务，包括为其分配工作器的ID。例如，GET /connectors/file-source/status请求显示名为file-source的连接器的状态:

{

"name":"file-source",

"connector": {

    "state":"RUNNING",

    "worker_id":"192.168.1.208:8083"

},

"tasks": [

    {

    "id": 0,

    "state":"RUNNING",

    "worker_id":"192.168.1.209:8083"

    }

]

}

连接器及其任务将状态更新发布到共享主题(使用status.storage.topic配置)，集群中的所有worker都将监视该主题。因为worker异步使用此主题，所以在通过status API看到状态更改之前，通常会有(短暂的)延迟。连接器或其任务之一可能存在以下状态：

· **UNASSIGNED**	**：**连接器/任务尚未分配给worker。

· **RUNNING**		**：**连接器/任务正在运行。

· **PAUSED**		**：**连接器/任务已在管理上暂停。

· **FAILED**		**：**连接器/任务失败（通常是通过引发异常，这在状态输出中报告）。

· **DESTROYED**	**：**该连接器/任务已通过管理方式删除，将不再出现在Connect集群中。

在大多数情况下，连接器和任务状态会匹配，尽管在发生更改或任务失败时的短时间内它们可能会有所不同。例如，当第一次启动连接器时，在连接器及其任务全部转换为RUNNING状态之前，可能会有明显的延迟。当任务失败时，状态也会发散，因为Connect不会自动重新启动失败的任务。要手动重新启动连接器/任务，可以使用上面列出的API重新启动。请注意，如果尝试在进行重新平衡时重新启动任务，则Connect将返回409（冲突）状态代码。您可以在重新平衡完成后重试，但是由于重新平衡可以有效地重新启动集群中的所有连接器和任务，因此可能没有必要。

暂时停止连接器的消息处理有时很有用。例如，如果远程系统正在维护中，则源连接器最好停止轮询获取新数据，而不是用异常垃圾消息填充日志。对于此用例，Connect提供了一个暂停/恢复API。当源连接器暂停时，Connect将停止轮询获取其他记录。当接收器连接器暂停时，Connect将停止发送新消息。暂停状态是持久化的，因此，即使您重新启动集群，连接器也不会再次开始消息处理，直到恢复任务为止。请注意，所有连接器的连接可能会延迟 的任务已转换为"暂停"状态，因为它们可能需要一些时间才能完成暂停时正在进行的任何处理。此外，失败的任务在重新启动之前不会转变为PAUSED状态。
