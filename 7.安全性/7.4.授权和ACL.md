Kafka附带了可插入的Authorizer和使用Zookeeper存储所有ACL的现成的Authorizer实现。通过authorizer.class.name在server.properties中进行设置来配置授权者。要启用现成的实现，请使用:

authorizer.class.name = kafka.security.auth.SimpleAclAuthorizer

Kafka ACL以以下通用格式定义:"主体P是与主机资源H在与ResourcePattern RP匹配的任何资源R上来自主机H的[允许/拒绝]操作O"。您可以在KIP-11中阅读有关acl结构的更多信息，并在KIP-290中阅读有关资源模式的更多信息。为了添加，删除或列出ACL，您可以使用Kafka授权程序CLI。默认情况下，如果没有ResourcePatterns与特定的资源R匹配，则R没有关联的ACL，因此除超级用户外，任何人都不能访问R。如果要更改该行为，可以在server.properties中包括以下内容。

allow.everyone.if.no.acl.found = true

也可以像下面这样在server.properties中添加超级用户（请注意，分隔符为分号，因为SSL用户名可能包含逗号）。默认PrincipalType字符串"User"区分大小写。

super.users=User:Bob;User:Alice

### 1.1.1. **自定义SSL用户名**

默认情况下，SSL用户名的格式为"CN = writeuser，OU =未知，O =未知，L =未知，ST =未知，C =未知"。可以通过ssl.principal.mapping.rules在server.properties中设置自定义规则来更改它。此配置允许将X.500专有名称映射为短名称的规则列表。将按顺序评估规则，并且使用与专有名称匹配的第一个规则将其映射为短名称。列表中以后的所有规则都将被忽略。

格式ssl.principal.mapping.rules是一个列表，其中每个规则均以"RULE:"开头，并包含以下格式的表达式。默认规则将返回X.500证书专有名称的字符串表示形式。如果专有名称与模式匹配，则替换命令将在名称上运行。这也支持小写/大写选项，以强制转换后的结果全部为小写/大写。这是通过在规则末尾添加"/L"或"/U"来完成的。

RULE:pattern/replacement/

RULE:pattern/replacement/[LU]

示例ssl.principal.mapping.rules值包括:

RULE:^CN=(.*?),OU=ServiceUsers.*$/$1/,

RULE:^CN=(.*?),OU=(.*?),O=(.*?),L=(.*?),ST=(.*?),C=(.*?)$/$1@$2/L,

RULE:^.*[Cc][Nn]=([a-zA-Z0-9.]*).*$/$1/L,

DEFAULT

上述规则将专有名称"CN = serviceuser，OU = ServiceUsers，O =Unknown，L =Unknown，ST =Unknown，C =Unknown"转换为"serviceuser"和"CN = adminUser，OU = Admin，O =Unknown，L ="adminuser @ admin"的"Unknown，ST =Unknown，C =Unknown"。

对于高级用例，可以通过在server.properties中设置自定义的PrincipalBuilder来自定义名称，如下所示。

principal.builder.class=CustomizedPrincipalBuilderClass

### 1.1.2. **自定义SASL用户名**

默认情况下，SASL用户名将是Kerberos主体的主要部分。可以通过sasl.kerberos.principal.to.local.rules在server.properties中设置自定义规则来更改它。的格式sasl.kerberos.principal.to.local.rules是列表，其中每个规则的工作方式与[Kerberos配置文件（krb5.conf）中](http://web.mit.edu/Kerberos/krb5-latest/doc/admin/conf_files/krb5_conf.html)的auth_to_local相同。这也支持附加的小写规则，以强制将转换后的结果全部转换为小写。这是通过在规则末尾添加"/ L"来完成的。检查以下格式的语法。每个规则都以RULE:开头，并包含以下格式的表达式。有关更多详细信息，请参见kerberos文档。

RULE:[n:string](regexp)s/pattern/replacement/

RULE:[n:string](regexp)s/pattern/replacement/g

RULE:[n:string](regexp)s/pattern/replacement//L

RULE:[n:string](regexp)s/pattern/replacement/g/L

添加规则以将user@MYDOMAIN.COM正确转换为用户，同时还保留默认规则的示例如下:

sasl.kerberos.principal.to.local.rules=RULE:[1:$1@$0](.*@MYDOMAIN.COM)s/@.*//,DEFAULT

### 1.1.4. **例子**

· **添加Acl**

假设您要添加acl"允许Principals User:Bob和User:Alice对IP 198.51.100.0和IP 198.51.100.1执行对topicTest-Topic的操作读写"。您可以通过使用以下选项执行CLI来实现:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --add --allow-principal User:Bob --allow-principal User:Alice --allow-host 198.51.100.0 --allow-host 198.51.100.1 --operation Read --operation Write --topic Test-topic

默认情况下，所有不具有允许访问资源操作的显式acl的主体都将被拒绝。在极少数情况下，定义了允许访问除某些主体以外的所有主体的allow acl，我们将不得不使用--deny-principal和--deny-host选项。例如，如果我们要允许所有用户读取Test-topic，但仅拒绝IP 198.51.100.3中的User:BadBob，则可以使用以下命令进行操作:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --add --allow-principal User:* --allow-host * --deny-principal User:BadBob --deny-host 198.51.100.3 --operation Read --topic Test-topic

请注意，-allow-host和deny-host仅支持IP地址（不支持主机名）。上面的示例通过将--topic [topic-name]指定为资源模式选项来向topic添加ACL。同样，用户可以通过指定--cluster将acls添加到集群中，并通过指定--group [group-name]添加到消费者组中。您可以在特定类型的任何资源上添加ACL，例如，假设您要添加ACL"允许主用户:Peter可以从IP 198.51.200.0的任何topic中产生"，您可以使用通配符资源"*"来实现，例如，通过使用以下选项执行CLI:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --add --allow-principal User:Peter --allow-host 198.51.200.1 --producer --topic *

您可以在带前缀的资源模式上添加ACL，例如，假设您要添加ACL"允许主体用户:Jane到名称从任何主机以'Test-'开头的任何topic"。您可以通过使用以下选项执行CLI来实现:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --add --allow-principal User:Jane --producer --topic Test- --resource-pattern-type prefixed

注意，--resource-pattern-type默认为'literal'，这只会影响名称完全相同的资源，或者对于通配符资源名称为'*'的情况而言，会影响具有任何名称的资源。

· **删除ACL**

删除ACL几乎相同。唯一的区别是用户必须指定--remove选项而不是--add选项。要删除上面第一个示例添加的acl，我们可以使用以下选项执行CLI:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --remove --allow-principal User:Bob --allow-principal User:Alice --allow-host 198.51.100.0 --allow-host 198.51.100.1 --operation Read --operation Write --topic Test-topic

如果要删除添加到上述前缀资源模式中的acl，我们可以使用以下选项执行CLI:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --remove --allow-principal User:Jane --producer --topic Test- --resource-pattern-type Prefixed

· **列出ACL**

我们可以通过为资源指定--list选项来列出任何资源的ACL。要列出文字资源模式Test-topic上的所有ACL，我们可以使用以下选项执行CLI:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --list --topic Test-topic

但是，这只会返回已添加到此确切资源模式的ACL。可能存在影响访问topic的其他ACL，例如，topic通配符'*'上的任何ACL，或带前缀资源模式上的任何ACL。可以显式查询通配符资源模式上的Acl:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --list --topic *

但是，不一定可以在与Test-topic匹配的前缀资源模式上显式查询acl，因为此类模式的名称可能未知。我们可以使用'--resource-pattern-type match' 列出*所有*影响Test-topic的ACL，例如

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --list --topic Test-topic --resource-pattern-type match

这将列出所有匹配的文字，通配符和前缀资源模式的ACL。

· **添加或删除委托人作为生产者或****消费者**

最常见的ACL管理用例是添加/删除委托人作为生产者或消费者，因此我们添加了方便的选项来处理这些情况。为了将User:Bob添加为Test-topic的生产者，我们可以执行以下命令:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --add --allow-principal User:Bob --producer --topic Test-topic

类似地，要将Alice添加为消费者组Group-1的Test-topic消费者，我们只需传递--consumer选项:

bin/kafka-acls.sh --authorizer-properties zookeeper.connect=localhost:2181 --add --allow-principal User:Bob --consumer --topic Test-topic --group Group-1

请注意，对于消费者选项，我们还必须指定消费者组。为了从生产者或消费者角色中删除主体，我们只需要传递--remove选项。

· **基于AdminClient API的ACL管理**

对ClusterResource具有"更改"权限的用户可以使用AdminClient API进行ACL管理。kafka-acls.sh脚本支持AdminClient API来管理ACL，而无需直接与zookeeper / authorizer进行交互。可以使用**--bootstrap-server**选项执行上述所有示例。例如:

bin/kafka-acls.sh --bootstrap-server localhost:9092 --command-config /tmp/adminclient-configs.conf --add --allow-principal User:Bob --producer --topic Test-topic

bin/kafka-acls.sh --bootstrap-server localhost:9092 --command-config /tmp/adminclient-configs.conf --add --allow-principal User:Bob --consumer --topic Test-topic --group Group-1

bin/kafka-acls.sh --bootstrap-server localhost:9092 --command-config /tmp/adminclient-configs.conf --list --topic Test-topic

### 1.1.5. **授权原语**

协议调用通常在Kafka中的某些资源上执行某些操作。需要知道操作和资源以建立有效的保护。在本节中，我们将列出这些操作和资源，然后列出它们与协议的组合以查看有效的方案。

#### 1.1.5.1. **Kafka****行动**

有一些操作原语可用于建立特权。这些可以与某些资源匹配，以允许给定用户的特定协议调用。这些是:

· Read

· Write

· Create

· Delete

· Alter

· Describe

· ClusterAction

· DescribeConfigs

· AlterConfigs

· IdempotentWrite

· All

#### 1.1.5.2. **Kafka****的资源**

上面的操作可以应用于以下描述的某些资源。

· **topic:**这仅表示一个topic。作用于topic的所有协议调用（例如阅读，编写topic）都需要添加相应的特权。如果topic资源存在授权错误，则将返回TOPIC_AUTHORIZATION_FAILED（错误代码:29）。

· **组****:**代表broker中的消费者组。与消费者组配合使用的所有协议调用（例如加入组）必须在topic中对该组具有特权。如果未赋予特权，则协议响应中将返回GROUP_AUTHORIZATION_FAILED（错误代码:30）。

· **集群:**此资源代表集群。影响整个集群的操作（如受控关闭）受集群资源特权的保护。如果集群资源上存在授权问题，则将返回CLUSTER_AUTHORIZATION_FAILED（错误代码:31）。

· **TransactionalId****:**此资源表示与事务相关的操作，例如提交。如果发生任何错误，那么broker将返回TRANSACTIONAL_ID_AUTHORIZATION_FAILED（错误代码:53）。

· 委托令牌**:**这代表集群中的委托令牌。诸如描述委派令牌之类的操作可以受到委派令牌资源上的特权的保护。由于这些对象在Kafka中有一些特殊的行为，建议您阅读 [Authentication上的"使用委托令牌"中的](#security_delegation_token)[KIP-48](#KIP-48DelegationtokensupportforKafka-DescribeDelegationTokenRequest) 和相关的上游文档。
