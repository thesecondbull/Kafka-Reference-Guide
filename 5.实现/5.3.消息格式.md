消息（也称为记录）始终成批写入。一批消息的技术术语是一个记录批（record batch），并且一个记录批包含一个或多个记录。在蜕化的用例下，我们可以有一个只包含单个记录的记录批。记录批和记录具有自己的 header。每个文件的格式如下所述。

### 1.1.1. **记录批****（****Record Batch****）**

以下是RecordBatch的磁盘格式。

baseOffset: int64

batchLength: int32

partitionLeaderEpoch: int32

magic: int8 (current magic value is 2)

crc: int32

attributes: int16

    bit 0~2:

        0: no compression

        1: gzip

        2: snappy

        3: lz4

        4: zstd

    bit 3: timestampType

    bit 4: isTransactional (0 means not transactional)

    bit 5: isControlBatch (0 means not a control batch)

    bit 6~15: unused

lastOffsetDelta: int32

firstTimestamp: int64

maxTimestamp: int64

producerId: int64

producerEpoch: int16

baseSequence: int32

records: [Record]

请注意，启用压缩后，被压缩的记录数据将根据记录数直接序列化。

CRC涵盖了从attributes到批次结束的数据（即，CRC之后的所有字节）。它位于magic字节之后，这意味着在决定如何解释批处理长度和magic字节之间的字节之前，客户端必须解析magic字节。当为代理接收到的每个批次分配该字段时，为了避免重新计算CRC，在CRC计算中不包括分区leader epoch字段。CRC-32C（Castagnoli）多项式用于计算。

关于压缩：与旧的消息格式不同，当清理日志时，magic v2及更高版本保留原始批处理中的第一个和最后一个offset/序列号。为了能够在重新加载日志时恢复生产者的状态，这是必需的。例如，如果我们没有保留最后的序列号，那么在分区引导失败后，生产者可能会看到OutOfSequence错误。必须保留基本序列号以进行重复检查（代理通过验证传入批次的第一个和最后一个序列号与该生产者的最后一个序列号匹配来检查传入的Produce请求是否重复）。因此，当批中的所有记录都被清除，但为了保留生产者的最后序列号，仍然保留批中的记录时，日志中可能有空的批。这里有一个奇怪的地方，那就是baseTimestamp字段在压缩期间没有保留，所以如果压缩了批处理中的第一条记录，那么它就会改变。

#### 1.1.1.1. **控制批（Control Batches）**

一个控制批（Control Batches）包含一个称为控制记录的记录。控制记录不应传递给应用程序。取而代之的是，消费者使用它们来过滤掉中止的事务消息。

控制记录的键符合以下schema：

version: int16 (current version is 0)

type: int16 (0 indicates an abort marker, 1 indicates a commit)

控制记录值的模式依赖于type。该值对于客户端是不透明的。

### 1.1.3. **旧****的****消息****格式**

在Kafka 0.11之前，消息被传输并将其存储在*消息集中*。在消息集中，每条消息都有其自己的元数据metadata。请注意，尽管消息集被表示为数组，但它们没有像协议中的其他数组元素一样以int32数组大小开头。

**消息集：**

MessageSet (Version: 0) => [offset message_size message]

    offset => INT64

    message_size => INT32

    message => crc magic_byte attributes key value

        crc => INT32

        magic_byte => INT8

        attributes => INT8

            bit 0~2:

                0: no compression

                1: gzip

                2: snappy

            bit 3~7: unused

        key => BYTES

        value => BYTES

MessageSet (Version: 1) => [offset message_size message]

    offset => INT64

    message_size => INT32

    message => crc magic_byte attributes key value

        crc => INT32

        magic_byte => INT8

        attributes => INT8

            bit 0~2:

                0: no compression

                1: gzip

                2: snappy

                3: lz4

            bit 3: timestampType

                0: create time

                1: log append time

            bit 4~7: unused

        timestamp =>INT64

        key => BYTES

        value => BYTES

在Kafka 0.10之前的版本中，唯一受支持的消息格式版本（在magic值中表示）为0。在版本0.10中引入了带有时间戳支持的消息格式版本1。

· 与上述版本2相似，attributes的最低位表示压缩类型。

· 在版本1中，生产者应始终将时间戳类型位设置为0。如果将 topic配置为使用日志追加时间，（通过代理级别的配置log.message.timestamp.type = LogAppendTime或 topic级别的配置message.timestamp.type= LogAppendTime），代理将覆盖消息集中的时间戳类型和时间戳。

· attributes的最高位必须设置为0。

在消息格式版本0和1中，Kafka支持递归消息以启用压缩。在这种情况下，必须设置消息的attributes以指明压缩类型，value字段将包含使用该压缩的消息集。我们通常将嵌套消息称为"内部消息"，将包装消息称为"外部消息"。请注意，对于外部消息，键应为null，其offset将是最后一个内部消息的offset。

当接收到递归版本0消息时，代理将它们解压缩，并且每个内部消息将分别分配一个offset。在版本1中，为避免服务器端重新压缩，仅为包装消息分配一个offset。内部消息将具有相对offset。可以使用外部消息的offset来计算内部消息的绝对offset。

crc字段包含后续消息字节（即从magic字节到值）的CRC32（而不是CRC-32C）。
